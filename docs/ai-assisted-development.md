# AI 辅助开发与 Vibe Coding 约定

本项目欢迎用自然语言快速表达意图，也欢迎 AI 参与调研、编码、测试和文档维护。这里的 Vibe Coding 不是“凭感觉直接提交”，而是把人的意图快速变成一组可阅读、可运行、可推翻的工程证据。

## 目标

- **快**：先打通最小端到端链路，缩短从想法到可体验结果的距离。
- **稳**：文件扫描、回收和移动的安全边界不能被速度牺牲。
- **可审**：评审者不需要重放整段 AI 对话，也能理解改了什么、为什么、如何验证。
- **可接手**：换一个人或 AI，只读仓库文档和代码即可继续工作。

## 人与 AI 的职责

| 角色 | 负责 | 不应委托出去 |
|---|---|---|
| 提出者 / 产品负责人 | 用户价值、优先级、验收条件 | 高风险操作的最终授权 |
| AI 助手 | 检索事实、比较方案、实现、执行验证、记录证据 | 自行批准需求、伪造测试、隐瞒不确定性 |
| 评审者 | 检查范围、风险、可维护性和测试证据 | 仅凭“AI 说通过了”放行 |
| 使用者 | 在小范围数据上试用并反馈 | 用唯一副本或无备份数据做首次验证 |

AI 生成代码不天然更差，也不天然可信。是否合入只看需求是否明确、改动是否可审、证据是否可复现、安全边界是否守住。

## 把想法写成可执行契约

开始前用五句话对齐：

1. **目标**：谁遇到什么问题，希望得到什么结果？
2. **范围**：本次明确要改哪些行为或文件？
3. **非目标**：哪些相邻问题暂时不处理？
4. **约束**：安全、兼容、性能、平台和依赖边界是什么？
5. **验收**：用什么命令或操作可以证明完成？

示例：

```text
目标：让 GitHub 读者无需下载 HTML 就能看清架构图。
范围：导出 SVG 与高分辨率 PNG，调整 README 入口。
非目标：不改变运行时架构和应用代码。
约束：Archify 保持仓库级安装；README 不链接 HTML 源作为主入口。
验收：SVG 可无损缩放、PNG 可读、链接存在、Archify receipt 为 canonical。
```

## 轻量分级

| 级别 | 典型改动 | 必需材料 |
|---|---|---|
| L0 | 错别字、链接、纯格式、依赖锁定文件的机械更新 | 清晰 diff + 对应检查 |
| L1 | 局部缺陷、单模块行为调整、低风险脚本 | 问题根因、实现说明、测试证据 |
| L2 | 新功能、跨模块重构、安全边界、数据格式或不可逆决策 | `docs/changes/` 变更提案 + 方案比较 + 风险/回滚 + 验收证据 |

级别按风险而不是代码行数判断。修改“删除、移动、覆盖、Git 一致性、审计”任一行为，至少按 L2 处理。

## 四阶段证据链

### 1. 调研

- 先读 `AGENTS.md`、相关 `docs/`、当前 Git 状态、现有实现和依赖。
- L2 至少比较两个可行方案，说明各自成本和落选原因。
- 外部事实附来源和版本；仓库事实引用具体路径。
- 把未知项写成未知项，不用肯定语气补全空白。

### 2. 方案

- 说明目标、非目标、影响面、数据流、安全风险和回滚边界。
- 优先选择最简单的完整方案；每一步应能单独检查或回退。
- 安全策略、架构或依赖变化在实施前由人评审。

### 3. 实施

- 保持提交小而完整，不混入无关清理。
- 发现方案不成立时回写决策和风险，不在代码里悄悄换方向。
- 同步更新用户手册、安全说明、架构图、测试和变更记录。

### 4. 验证与放行

- 证据写成“执行了什么 + 得到什么”，不写尚未执行的测试计划冒充结果。
- AI 可以运行检查并解释结果，但最终评审由另一个人完成。
- 失败、跳过和环境限制都如实记录；局部通过不表述为整体完成。

## 最低证据矩阵

| 变更类型 | 最低验证 |
|---|---|
| Rust 逻辑 | `cargo fmt`、`cargo clippy`、`cargo test` |
| 回收 / 移动 | 正常、拒绝、取消、失败、回滚、审计路径 |
| UI | 关键操作路径；视觉变化附截图 |
| 架构 | Archify validate / deliver / export / visual-check 与人工检查 |
| 性能 | 可复现输入、命令、环境和前后数据 |
| 文档 | 链接、命令、版本和资源存在性 |

## 如何让使用者和维护者愿意接受

### 先展示价值，不先展示技术

README 和演示从真实任务开始：找到磁盘大文件、确认重复副本、预览工程移动计划。技术栈和内部模块放在价值说明之后。

### 让风险看得见

- 明确哪些操作只读、哪些会改文件。
- 真实变更前展示计划、数量、源路径和目标路径。
- 默认采用可恢复或拒绝策略；高风险选项由用户显式开启。
- 已知限制和失败结果与成功功能同样公开。

### 用可复现证据建立信任

- 提供从源码运行、Release 构建、自检和测试命令。
- PR 写实际测试结果；UI 和架构变化附图。
- 保留审计日志与 CSV 导出，让用户能复核发生过什么。
- 小 PR、单一意图、清楚 commit，让评审者可以逐步接受，而不是一次相信整个生成结果。

### 对 AI 使用保持透明

PR 说明 AI 参与了调研、编码、文档还是测试，并写明人工复核的范围。不要粘贴冗长对话或把工具品牌当质量证明；真正有用的是可检查的 diff、设计取舍和测试证据。

## PR 中的 AI 声明

建议填写：

```text
AI 参与：调研 / 设计 / 编码 / 测试 / 文档（按实际选择）
人工复核：已检查的模块或行为
未覆盖：没有运行的平台、场景或人工验证
```

这不是给 AI 代码贴标签，而是帮助评审者把注意力放到未经人工检查、依赖环境或高风险的部分。

## 禁止的反模式

- 跳过现有代码和文档，直接根据模型印象重写。
- 用更长的提示词代替需求、设计和测试。
- 在实现过程中静默扩大范围或顺手重构无关代码。
- 声称“测试通过”却不给命令与结果，或把编译成功当成行为验证。
- 让同一个 AI 既实现又代表人类批准高风险变更。
- 为了兼容假想使用者保留两套实现、无消费者的开关或临时架构。
- 把凭据、用户文件内容、真实私人路径或敏感日志放入提示、Issue、PR 或 commit。
